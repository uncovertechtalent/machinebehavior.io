    Continuous conformity · 2026-11-24 · public comments on ISO/IEC DIS 23282

    What should a standard for evaluating language systems require of a system in operation?

    Six comments on the ISO draft on evaluating language systems, kept as a public reference. They missed DIN's national comment window.

    It should name the configuration it tested, re-test after every change and on a fixed schedule, check its automatic graders before trusting them, date its reference data, include a run that does not look like a test, and record results in a form a machine can compare. Stefan Coetzee wrote these six points as comments on ISO/IEC DIS 23282, "Evaluation methods for accurate natural language processing systems", and published them here on 2026-11-24. They did not reach the German vote: DIN's national comment period ran from 2026-09-04 to 2026-11-04, about three weeks before the international and European enquiry closed (DIN, by email, 2026-11-26).

    This page is the public record of those comments. When ISO/IEC 23282 is published, each point can be checked against the final text.

    What the comments address, and where they were meant to go

    • Draft: ISO/IEC DIS 23282, Artificial Intelligence, Evaluation methods for accurate natural language processing systems. Catalogue page: iso.org/standard/87387.html.
    • Committees: ISO/IEC JTC 1/SC 42/JWG 5, a joint working group of SC 42 and ISO/TC 37. German mirror: DIN NA 105-00-06-01 GAK, Natural Language Processing.
    • Route: DIN Norm-Entwurfs-Portal. The national comment period ran from 2026-09-04 to 2026-11-04. DIN closes it before the ISO and CEN date so the German vote can be consolidated in time; the date ISO and CEN publish for the enquiry is not the date a commenter in Germany has to meet.
    • Status of the commenter: individual expert, not on behalf of a company or a committee.
    • Form: seven entries, all at clause level "General": one disclosure and six comments. The text below is the text prepared for submission.

    Why every comment says "General"

    The standards that compliance as code would encode are licensed against machine reading. DIN Media's terms (AGB section 5.4) require "the separate acquisition of a corresponding AI licence" for machine processing of standards. The comments were drafted with AI assistance, so no text of the draft went into any AI tool, and no comment cites a clause. The prepared submission says so in its first entry:

    Disclosure. These comments were drafted with AI assistance and are submitted by an individual expert, who is responsible for them. No text of the draft was given to any AI tool, because DIN Media's terms (AGB section 5.4) require a separate licence for machine processing of standards. The comments are therefore made at the general level, without clause references. A public copy of these comments and this note is kept at machinebehavior.io/conformity/din-23282/.

    How that licence rule reached the working sessions, and what they did with it, is documented in Case 12: A Licence Rule Relayed Mid-Task.

    The six comments

    1. Name the evaluated configuration

    technical comment · clause: General · Continuous Conformity CC-5.1, CC-5.2

    Comment. For systems built on a language model, the output depends on the full configuration in use: model version, system instructions, retrieved documents, tools and memory. A result for one configuration does not carry over to another configuration with the same model. The document should state what object the evaluation results apply to. If the document already covers this, please read this comment as support for that provision.

    Proposed change. Add the following requirement: "The evaluation report shall identify the evaluated configuration, including the model version, system instructions, retrieval sources and tools, by version or content hash. Results shall not be reported for a configuration other than the one evaluated."

    2. Re-evaluate after every change and on a schedule

    technical comment · clause: General · Continuous Conformity CC-7.1, CC-7.3

    Comment. Accuracy measured once before deployment does not show accuracy in operation. Configurations change after deployment (model updates by third parties, edits to instructions, new documents in retrieval). Regulation (EU) 2024/1689 requires that high-risk systems "perform consistently ... throughout their lifecycle" (Art. 15(1)) and that post-market monitoring allows the provider "to evaluate the continuous compliance" of the system (Art. 72(2)). If the document already covers this, please read this comment as support for that provision.

    Proposed change. Add a subclause on re-evaluation: "The evaluation should be repeated after every change to the evaluated configuration and at an interval stated by the user of this document during operation. The report shall state the date of evaluation and the configuration identifiers, so that results from successive evaluations can be compared."

    3. Validate automatic graders

    technical comment · clause: General · Continuous Conformity CC-6.5

    Comment. Automatic metrics and model-based graders ("LLM as judge") can fail silently: a grader that cannot detect a failure produces passing results. The validity of the grader is part of the technical resources of the evaluation. If the document already covers this, please read this comment as support for that provision.

    Proposed change. Add the following requirement: "Before use, and after any change, each automatic grader shall be checked against a set of cases with known correct results and a set with known incorrect results. The report shall include the outcome of this check."

    4. Give reference data a source and a verification date

    technical comment · clause: General · Continuous Conformity CC-8.2, CC-8.4

    Comment. For NLP systems that answer from documents (retrieval-augmented systems), the reference answers depend on documents that change over time. A reference answer that was correct when written can be wrong at the time of evaluation, which makes the accuracy result invalid. If the document already covers this, please read this comment as support for that provision.

    Proposed change. Add the following requirement: "Where reference data are derived from documents that can change, each reference item shall record its source and the date it was last verified against that source. Reference items older than a stated interval shall be re-verified before use."

    5. Include a condition that does not look like a test

    technical comment · clause: General · Continuous Conformity CC-6.4

    Comment. Language models can behave differently when the input shows that it is a test (Greenblatt et al., arXiv:2412.14093; Meinke et al., arXiv:2412.04984). An evaluation run only under visible test conditions may not show behaviour in use. If the document already covers this, please read this comment as support for that provision.

    Proposed change. Add as a recommendation: "Where feasible, evaluations should include a condition in which the input gives no indication that it is part of an evaluation. Where both conditions are run, the report should state the difference between them."

    6. Record results in machine-readable form

    general comment · clause: General · Continuous Conformity CC-12.5

    Comment. Evaluation reports in free text are hard to compare across repeated evaluations and between parties. Open machine-readable formats for assessment results exist; the NIST OSCAL assessment model "supports information from periodic and continuous assessments" (pages.nist.gov/OSCAL). If the document already covers this, please read this comment as support for that provision.

    Proposed change. Add as a note or recommendation: "Evaluation results should be recorded in a structured, machine-readable form, so that repeated evaluations and evaluations by different parties can be compared. An open format for assessment results, such as the NIST OSCAL Assessment Results model, can be used."

    Where the six points come from

    Each comment is one requirement of Continuous Conformity for Deployed AI Systems, a reference text Stefan Coetzee published at machinebehavior.io on 2026-10-09: 36 requirements for testing a deployed AI system, and the knowledge it runs on, on every change and on a fixed schedule, decided by someone other than the system, with records a third party can rerun. The comments do not use the term; they carry its requirements to the ISO draft on evaluating language systems.
