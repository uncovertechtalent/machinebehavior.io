    Zero trust

    owner Stefan Coetzeecreated 2026-10-13updated 2026-10-13reviewed 2026-10-13review by 2027-01-117 min readexplanationstate: partial

    The principle

    Nothing is trusted because of where it comes from. An input, an identity, a dependency, and a report are each verified at the boundary where they are used, whether they arrive from the internet, from a colleague, from a vendor, or from an agent session. Each actor, whether a person, a job, or an agent, gets the least access its job needs, for the shortest time, and each use is recorded. Nobody gets access for being on the right network, and nobody accepts a result because it comes from a familiar name or shows a green status.

    Source: the Zero Trust section of Security and Defense in Depth and Trust Boundaries, pillar 8 of the framework. Reports are covered by Truth, verified, working. References: NIST's Zero Trust Architecture (SP 800-207), Google's BeyondCorp, and the least privilege chapter of Building Secure and Reliable Systems.

    On this platform

    Dependencies:

    • Actions pinned and allowlisted. Every action from outside the repository is pinned to a full 40-character commit SHA, and its owner must be on the allowlist in conformity/site-tier.json, which holds one owner today, actions. The gate checks actions.pinned and actions.owners block the deploy on a tag or branch reference or an unlisted owner (Conformity gate; #59, #61, pins in #56). Dependabot proposes new pins monthly, and a new owner needs its own reviewed pull request.
    • The workflow checked as code. A zizmor job reads .github/ for template injection, broad permissions, persisted credentials, and unpinned references on every run, installed from hash-pinned wheels (#65). It is advisory: the ruleset does not require it and the deploy does not wait for it (#82). Dependabot cannot yet update the zizmor and Claude Code pins under .github/, so those two pins age until someone moves them by hand (#77).
    • The other sites pin the gate. tychat.io and uncovertechtalent.com run this gate pinned to a commit of main, so a change to the gate reaches them only when someone moves the pin.
    • No third party in the reader's browser. Pages load no script, font, or style from another company (ADR-0010).

    Identities and access:

    • Every change through a pull request and the gate. A ruleset on main requires a pull request and a passing Conformity checks job, and blocks force pushes and branch deletion; the repository allows squash merges only (ADR-0029). A pull request run checks the merge result and commits and deploys nothing.
    • One key per writer. The two automated writers that push to main, the gate's bot and the weekly probe record, each have their own deploy key, the only bypass the ruleset allows. The workflow passes the bot's key to the checkout only on runs from main, and the Pages environment accepts deployments from main and gh-pages only.
    • Permissions per job. The workflow starts with no permissions (permissions: {}), and each job names what it needs, with the reason beside each line: the checks job writes contents, for the bot commit when the deploy key is missing; the deploy job reads contents, writes to Pages, writes the OIDC token that the Pages deploy needs, and reads Actions runs and issues for the deploy feed and the board snapshots; the zizmor job reads contents.
    • Agent sessions within limits. The shared agent settings deny reading or editing .env files and the secrets/ folder, deny merges through gh api, and ask before every gh pr merge (Agents in this repository). The rules load only in sessions started in this checkout and match tool and command patterns. They guard a cooperating agent and are no sandbox, so the required check on main still runs before every merge.
    • Paths allowlisted at the front door. The public Grafana sits behind a proxy that passes only the shared dashboard paths and answers everything else with 404 (Access model).

    Inputs and reports:

    • Agent-written pages are inputs. The gate checks every page an agent session writes before a reader sees it, by the same rules as the operator's pages.
    • Private terms kept out. Names that must stay private (prospective employers or clients, internal shorthand, and private hosts) do not enter the public repository. A pre-push hook on the operator's machine stops a push that adds one (CTO powersuit #2), and the private.terms check scans the tree and the build output in a dry run (#64). The term list stays outside every repository.
    • Third-party text quarantined. Since 2026-10-13 the operator's agent harness keeps raw third-party text that is saved for later (posts, e-mails, and web pages) in a store outside the knowledge base. A session reads a stored item only through a summarising model that has no tools and returns a fixed-shape summary, with measured fields computed in code and a flag for text aimed at an AI model. A hook denies the direct reads of the store that it recognises. The hook guards the tool calls of a cooperating agent and is no sandbox, and text pasted into a session reaches that session before it can be stored. It runs on the operator's machine and is not part of this repository; a packaged version for other teams, the skill /security:quarantine, is in review in the CTO powersuit (#15).
    • Reports are claims until probed. A session's completion message, a review comment, or a status line is a claim until someone checks the artifact (Truth, verified, working). The change review is input to the merge decision and never evidence of conformity, and no requirement of the gate may list it. The review job that reads pull request text gives the model no write token, no shell, and no network; until that job has its key, the review runs on the operator's machine (Software delivery lifecycle).

    State

    Partial. The supply chain, the change path, and the job permissions follow the principle, and the gate enforces most of it. Five parts are missing:

    • One GitHub account carries the operator and every agent session, so GitHub cannot tell their actions apart or give a session less access than the operator (#79).
    • CONFORMITY_PUSH_KEY is a repository secret, so a workflow run on any branch can read it; the workflow's branch guard stops accidents only. Moving it to an environment limited to main is a settings change for the operator (#76).
    • A pull request from a branch of this repository runs with the workflow's write permissions, so its checks job holds a token that can write contents, and a pull request that edits .github/ or the gate configuration runs its own copy of the gate and can loosen it. For those paths, the person who merges is the only control (ADR-0029); a required review there needs a second identity first (#79).
    • The workflow security check is advisory: a zizmor finding on a pull request blocks neither the merge nor the deploy (#82).
    • The internal dashboards, Prometheus, and Loki are reachable from the home network only, so the network location grants access; the identity-aware design on the Access model page is not built (#83). Security headers wait on the hosting decision (#26).

    In a company of 10 to 200 people

    • Pin every third-party action, package, and image by digest, keep an allowlist of their owners, and let a bot propose the updates.
    • Give every person, job, and agent its own identity, with permissions that start at none and are added per job. Never share an account between a person and an automation.
    • Keep secrets in environments that only the protected branch can read, and prefer short-lived tokens from OIDC over stored keys.
    • When an agent with tools reads text from outside (tickets, e-mails, pull request bodies, web pages), give it a summary made in a sandbox, and never let that text start an action.
    • Replace network-based access to internal tools with an identity-aware proxy and a device check.
