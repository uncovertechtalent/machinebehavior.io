    Inside · Masthead · machinebehavior.io · 2026-10-16

    Masthead

    machinebehavior.io is a publishing house run on the engineering practices of a CTO: every change through a gate, every page with an owner, and every claim with a source. 6 seats, 1 holder today: Stefan Coetzee. Each seat reads some of the eight areas of the cockpit, its staff work runs on the open modules of the CTO powersuit, and the gates listed under the seat say where each one runs. The seats together are the C-suit: one suit per seat, the whole suit for a company. The seats are a data file, seats.json; a seat that moves to another person is one changed line in it.

    The seats

    One section per seat. The areas link to the same area on the cockpit. Machinery is the set of modules and skills that do the seat's staff work; the gates are the checks a change in the seat's scope passes before it ships, each marked with where it runs. A bundle is the seat's own suit over the shared modules, the part of the C-suit that one seat wears; none exists yet, so each seat lists its machinery by hand.

    Where a gate runs
    site gate
    runs in the deploy gate of this site on every push to main; a failing check keeps the previous build live
    module repository
    runs in the continuous integration of the CTO powersuit repository on every change
    pre-push
    runs on the holder's machine before every push, with data that never leaves it
    module
    ships with the named module and runs in the deploy gate of a repository that has fitted it; this site's gate does not run it
    policy
    a rule the holder follows by hand; its enforcement is an open item where one is named

    CEO

    Chief executive

    Holder: Stefan Coetzee · bundle: none yet

    • Direction

    Machinery

    • direction A weekly review that reads the tracker across all areas and writes the memo: what moved, what is blocked, the allocation of the week, and the decisions needed. A confirmed decision becomes a tracker item.
    • decisions Requests for comments, numbered decision records with supersede links, and a review of the decision log.
    • cockpit The queue of items that wait on the holder, one scorecard per area, and the trend: 14 days on the public cockpit, 12 weeks on the local one.

    Gates

    • direction.review-memo module Every review memo names its date and period, carries the four sections, and gives every decision a status.
    • decisions.adr-fields module Every decision record has a status, an owner, and a date. The decision records of this site live in its docs tree.

    CTO

    Chief AI and technology officer

    Holder: Stefan Coetzee · bundle: none yet

    • Delivery
    • Operations
    • Security and risk
    • AI

    Machinery

    • sdlc The lifecycle of a change: tickets, a change review on every pull request, a test strategy, and a release with a rollback plan.
    • gate The deploy gate: rules with pass and fail fixtures, run records, and a deploy job that waits for the gate.
    • docs Pages with an owner and review dates, runbooks, a sweep for stale pages, and a health page that lists the pages past review.
    • observability and reliability Dashboards as code, alert routes, availability targets per service, a status page, incidents, and postmortems.
    • security and compliance Workflow steps pinned to a commit and limited to an owner allowlist, a secrets scan, an access review, threat models, a quarantine for third-party text, a control map by clause number, and the legal baseline of a site.
    • ai-ops and red-team A shared harness for coding agents with narrow permissions, spend metered per request, a coordinator pattern, and pressure tests with a known right answer.

    Gates

    • actions.pinned site gate Every workflow step from outside the repository is pinned to a full commit.
    • actions.owners site gate Every workflow step comes from an owner on the allowlist.
    • deploy.gated site gate The deploy job waits for the gate; a failing check keeps the previous build live.
    • gate checks against fixtures module repository Every gate check of every module passes its pass fixture and fails its fail fixture.
    • release metadata module repository Every changed module raises its version, and the changelog names the release.
    • sdlc.traceability module Every change names a ticket or a decision. On this site, the pull request title carries the issue or the decision.
    • docs review fields policy Every page of the docs tree carries an owner and review dates; the health page lists the pages past review. A gate check on the fields is an open decision (issue 27).
    • security.secrets module No secret pattern in a tracked file.
    • reliability.service-catalog module Every service has an owner, an availability target, and a runbook.
    • observability.alert-routes module Every alert rule names a route and a runbook.
    • compliance.security-txt policy The security contact file exists and has not expired. This site has none yet (issue 12).
    • compliance.no-third-party policy No page loads a file from a third party (decision record ADR-0010 of this site). The module's check is not in this site's gate.
    • ai-ops.agent-settings module The shared agent settings carry no secret and no wildcard permission.
    • red-team.run-records module Every pressure-test run names the expected and the observed decision.

    PUBLISHER

    Publisher

    Holder: Stefan Coetzee · bundle: none yet

    • AI
    • Knowledge layer

    Machinery

    • aieo A plain index for agents, structured data that matches the visible page, a fixed query set probed against AI search engines, and predictions hashed before a page goes live.
    • site gate The conformity gate on every page of the house's sites, with its history in the open.
    • change review An advisory review of every pull request by the coding agent, with the pull request as files, no shell, and no network: in the pipeline once it has its key, from the holder's machine until then.
    • editorial standards The standards on this page: sources and verification, the gates every piece passes, and how corrections are made.

    Gates

    • rules.blocking site gate No service closer, filler idiom, or stage hook in the copy of any page.
    • placeholders site gate No placeholder text on any page.
    • site.consistency site gate A canonical link on every page, root-absolute links only, and every page in the sitemap.
    • predictions.hashes site gate Every prediction file matches its recorded hash.
    • private.terms pre-push A push that adds a private term stops on the holder's machine; the site gate runs the same check as a dry run only, with the list kept off the repository (issue 63).
    • approval policy The holder approves every change and merges it, or gives one session the go to merge it; no session merges without that go. Closing the merge path to sessions in the shared settings is an open item (issue 51).

    CKO

    Chief knowledge officer

    Holder: Stefan Coetzee · bundle: none yet

    • Knowledge layer

    Machinery

    • vault A plain-Markdown knowledge base with keyword and semantic search served to the coding agent, seeded from an interview, and fed by a skill that turns documents into linked one-idea notes.
    • quarantine Third-party text goes into a store outside every indexed folder; a local model with no tools returns a summary and never the raw text.
    • library The catalog of files and works in the local cockpit, rescanned on demand.
    • docs review sweep Stale pages found, checked against the system they describe, and dated again only after that check.

    Gates

    • vault.private-boundary module Private folders and notes are never indexed, never returned, and refused on read.
    • knowledge.freshness site gate The pages imported from the knowledge base carry at least one date, and the newest is within 90 days; the gate reports the result and does not block on it.

    The research layer

    Every seat's output passes one more layer that is not a seat. Stance filters hold the register and the position of the coding agent under pressure: plain professional language, no accommodation reflex, and a probe before every claim. An output filter calibrated to the holder scans every reply and every page the agent writes. Pressure tests with a known right answer grade the decision an AI feature takes. The calibration data stays private; a new holder calibrates their own.

    Editorial standards

    Sources and verification

    • Every factual claim on a page names its source, or the page says that no source exists. Primary sources come first: the document, the data file, the command output, and the person who was there.
    • A number carries its date and its source, in the text or in the page's data file. A figure without both does not go on a page.
    • A claim about a region or a language is checked in that language, against sources from that region.
    • A claim that was not verified is labelled as unverified on the page. A guess is never presented as a fact.
    • Text from outside the house (a post, an email, or a page) is read through a quarantine that returns a summary and never the raw text, so an instruction hidden in outside text cannot change a draft.
    • The knowledge base behind the pages stays private. A page cites public files only. A list of private terms stays on the holder's machine, where a hook stops a push that adds one of them.
    • A prediction is written and hashed before the page it tests goes live, so the record cannot be fitted to the result.

    The gates every piece passes

    • A page goes live only through a pull request; the one exception is the gate's own run record, which the gate commits after each run. The deploy job waits for the gate; a failing check leaves the previous build live.
    • The gate blocks on placeholder text, a page without a canonical link, a relative or file-suffixed internal link, a page missing from the sitemap, a prediction file whose hash differs from the record, an action not pinned to a full commit, an action from an owner outside the allowlist, and the blocking register rules: a service closer, a filler idiom, or a stage hook in the copy.
    • A change review by the coding agent runs on every pull request, with the pull request as files, no shell, and no network: in the pipeline once it has its key, from the holder's machine until then. It is advisory, and a decision already on record counts as a note.
    • The private-terms check runs on the holder's machine before every push, with a term list that never leaves it; the site gate runs the same check as a dry run only.
    • The holder of the publisher seat approves and merges every change. An agent session merges only on the holder's go in that session; this is a rule the sessions follow, and closing the merge path to them in the shared settings is an open item.
    • The gate's history is public at /conformity/: the result of every run and the open findings stay in the repository, and the full record of a run is kept for 90 days.

    Corrections

    • A factual error is fixed in place on the page. The page's history in version control is the record of what changed and when, linked from the footer of every page.
    • A prediction is never edited. A correction is a new file with a new hash; the old file and its hash stay.
    • Register and stance slips caught before publication, and who caught them, are logged at /slips/.
    • A reader reports an error through the report link in the footer of the page. The fix goes out through the same gate as the page did.
    • A page is never deleted to hide a claim. The history keeps every version.

    Masthead · data: seats.json, the public copy of the seats file of the house; the page blocks are written from it by a generator and checked against it before every deploy. The local cockpit is planned to read the private file. The CTO powersuit is a set of agent skills, one module per CTO function from the deploy gate to the hand-over, that one person uses to run a company's whole engineering platform.
