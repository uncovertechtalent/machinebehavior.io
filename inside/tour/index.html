    A five-minute tour of Inside

    Inside is the internal platform behind machinebehavior.io, run in public as a demo: a front page, a service catalog, docs with owners and review dates, a status page with incidents, a ticket board and a deploy gate. The tour has six stops. Each stop has a screenshot of the live page, taken on 2026-10-09, what to look at, what the same part does for a team of 10 to 200 people, and the link.

    Stop 1

    The front page

    30 s
    What to notice
    • The top row has the three sites, each with its gate result, the time from push to live and its open findings. The values are read from the records each site publishes, when the page loads.
    • Further down: the latest published pieces, a deploy feed of the last 12 runs, the apps, and five Grafana dashboards (deploys, Claude Code, local LLM, search engines, host).
    • One search box in the top bar covers the docs, the services and every page on the map. The / key moves the cursor there.

    In your company: the one page a new hire opens first, with what is live, what shipped today, where the docs are, and one search over all of it.

    Stop 2

    One service in the catalog

    60 s
    What to notice
    • The catalog has 12 services, one YAML file each. The build stops when a file has no owner, tier, lifecycle, or list of docs and runbooks.
    • Local LLM has an owner, tier 3, lifecycle production, its Grafana dashboard, three docs and two SLOs with targets: 99% of requests without an upstream error, and 95% of streamed requests with a first token within 4 s.
    • Its runbook list is empty, and the page shows "No runbook yet". The Conformity gate, a tier 1 service, links two runbooks.

    In your company: every service has a named owner, a tier that sets what gets fixed first, and its dashboard, runbooks and SLOs one click away, so the person on call starts from one page.

    Stop 3

    Owned, dated docs and a decision record

    60 s
    What to notice
    • Six spaces: Engineering, Observability, FinOps, Research, SRE Handbook, Standards and Compliance. Each hand-written page names an owner, the date of its last review, the date of its next review and its type (tutorial, how-to, reference or explanation, after Diátaxis), with a link to report an issue.
    • ADR-0002 records why a deploy waits for the checks: context, decision, consequences, status accepted. The decision records are numbered from ADR-0001; three are superseded and stay, each with a link to the record that replaced it.
    • The docs health page lists pages past their review date, due within 30 days, without an owner or without a type. On 2026-10-09 none was late and none lacked an owner; the pages imported from the knowledge vault are marked as never reviewed.

    In your company: docs that name who keeps them correct and when they were last checked, and one page that lists the ones going stale.

    Stop 4

    An incident, from status page to fix

    60 s
    What to notice
    • The entry: Prometheus reported USD 1,970,946.62 of Claude Code spend for a week whose per-request events sum to USD 1,003.45 at list price. No money moved; the meter was wrong, and the spend alert had been in firing state 73% of the time.
    • The cause, from the write-up: up to about 12 parallel Claude Code processes wrote one counter series, so each export from a process with a lower total counted as a reset, 230,328 times in a week.
    • The trail: the write-up with timeline and lessons, a runbook with the check queries, the fix in agent-observability c163b42 (spend and the alert now summed from per-request events), and ticket #29 on the board for the follow-up that is still open.

    In your company: each incident leaves the same trail, with a status entry, a blameless write-up, a runbook for the next time, the fix commit and a ticket for the open work.

    Stop 5

    A deploy that a failed check blocked

    60 s
    What to notice
    • On 2026-10-08 at 14:05 UTC a push to the map page failed the link check, because a link was written inside a JavaScript template string. The conformity job failed, the deploy job was skipped, and readers kept the previous build.
    • Finding F-1753a6d2d038 was opened on that commit and closed at 14:06:59 UTC, when the fix passed. Closed findings stay on the conformity page; the history of every run is kept in git. The status page records the same event as an incident with no reader impact.
    • Every push to the three sites runs the same checks before the deploy. They test the mechanical requirements of a working draft, Continuous Conformity for Deployed AI Systems (draft 0.3, 36 requirements), published as a reference text.

    In your company: a release that fails a check stops before customers see it, and the record shows which check failed, on which commit, and when the fix passed.

    Who built it, and how

    Stefan Coetzee built Inside on 2026-10-09, on top of machinebehavior.io and its deploy gate, which has gated every deploy since 2026-10-07.

    How: one operator. Stefan Coetzee sets the scope and makes the decisions; parallel Claude Code sessions, one per track of work, write the code and the pages; every push goes through the deploy gate. The stack is static pages on GitHub Pages, build scripts in Python with the standard library only, GitHub Issues for the board, and Prometheus, Loki and Grafana on one home server. The code, the decision records and the changelog are public in the repository.

    Stefan Coetzee offers this layer to teams of 10 to 200 people as CTO or fractional CTO: a service catalog, owned docs, a status page, a board and a deploy gate, as a bespoke build on the tools the team already uses.
